We want to model a concurrent system given by a lift of a building with $N$ floors and its users.
At each floor there could be multiple users (up to $M$) that want to use the lift.
The lift has a capacity of only one user at a time.
At each floor users have a button to call the lift. Inside the lift, the user has buttons to select the floor to go.
Users getting the lift on some floor should be served in order using a first-come-first-served/FIFO policy.
An alarm signal could be generated by a fire alarm system: in that case, the lift would interrupt current activities, move to the ground floor, open the door and wait, until some external signal about the alarm being solved is received.
## Finite State Process
We started the modeling process from an initial basic structure:
- A hand that moves above some switches and that can turn on and off one if it is above.

```
SWITCH = (on -> off -> SWITCH).
HAND = IDLE[1],
IDLE[i:1..4] = (s[i].on -> IDLE[i]
                |s[i].off -> IDLE[i]
                |move[to:1..4] -> IDLE[to]).

||SWITCHES(N=4) = (s[i:1..N]:SWITCH || HAND).
```

This correctly allows the execution of an action if and only if the hand process is "above" the respective switch index.
- In our case, the hand process is the elevator and the switches represent the floors of the building.

Starting from this, we added each system requirements step by step.

### FIFO Queue
Each level is designed as an indexed process of length $M$

```
QUEUE = SLOT[0],
SLOT[i:USERS] = (
    when (i < M) call -> wait -> enter_elevator -> select_floor -> exit -> SLOT[i + 1]
).
```

The current slot index represents the head of the queue.

### Elevator Single Capacity
In order to ensure that at any moment inside the elevator there is at most one user we separate the current elevator state in multiple sub-states:
- `IDLE[l:0..N]`: the cabin is empty and at the level `l`
- `IN_CABIN[i:0..N]`: the cabin is full and moving to the selected floor.

The `enter` action can only be performed in the `IDLE` state.
- An `exit` action is required before re-entering the `IDLE` state, hence, no user can enter while another is still inside.

```
IDLE[i:FLOORS] = (
	s[tmp:FLOORS].move_empty -> enter -> IN_CABIN[i]
),
IN_CABIN[i:FLOORS] = (
	move[to:FLOORS] -> exit[to] -> IDLE[to]
)
```

### Synchronization between Users and Elevator
> The current process composition is the following
```
||BUILDING = (
    s[i:0..M]:QUEUE
    || ELEVATOR
).
```

$M$ parallel `QUEUE` processes along with the `ELEVATOR` process.

The following action are in a shared alphabet.
- `QUEUE`: `enter`, `exit[to:0..N]`, `select_floor[to:0..N]`, `move[to:0..N]`
- The `ELEVATOR` process has the same actions with the addition of the process prefix: `s[i]`

Example:
- The elevator should be able to move only to the levels where a user pressed a button:

```
QUEUE = SLOT[0],
SLOT[i:USERS] = (
    when (i < M) call -> WAIT[i]
),
WAIT[i:0..M-1] = (
    move_empty -> ENTERING[i]	// elevator is coming to the level
),
// ...

ELEVATOR = IDLE[0],
IDLE[i:FLOORS] = (
	s[tmp:FLOORS].move_empty -> LOADING[tmp]
),
// ...
```
This way `move_empty` at a certain level is active only if a user at that level called the elevator and is waiting.

### Alarm System
> To model the allarm we added a third, very simple process:
```
// Elevator state
NORMAL = (
    alarm -> ALARM
),
// Alarm activated
ALARM = (resolve -> NORMAL).
```

In order to trigger the alarm in any state, each process is divided in small sub-processes.
- In each sub process there is a secondary possible choice that allows the activation of the allarm.

Example:
- In the user process (`QUEUE`) after entering the elevator the system can either wait for the user to select the target floor or trigger an allarm

```
SELECT[i:0..M-1] = (
    select_level[to:FLOORS] -> MOVING[i][to] // The elevator is moving with the user inside
   |alarm -> ALARM_MOVING[i]
),
// ...
```

The allarm can trigger in two different states:
- with no-one inside the cabin
- with a user inside the cabin

The two states differ in what is the sequence of action that can happen:
```
ALARM_ELEVATOR_FULL[i:FLOORS] = (
    s[i].move[0] -> open_door -> s[i].exit[0] -> AWAIT_SIGNAL
),
// Elevator is empty and the alarm triggers
ALARM_ELEVATOR = (move -> open_door -> AWAIT_SIGNAL),
```

Without this division the system could enter a **deadlock** as the user would be waiting for the `exit` operation that the elevator does not provide.

### Desing of the FLTL properties
> Most properties have the alarm exeption

In order to model this exeption we created a specific fluent `ALARM` that is true only when the system enters the alarm state, and false when the problem has been resolved.

The following assertion will require two different events to happen, either:
- The actual property is satisfied
- An allarm is triggered

Example:
```
assert LIVENESS_CALL = forall[f:0..N] [](CALLING[f] -> <>(s[f].enter || ALARM))
```

### Known Problems
> FIFO Queue
- The next user in the line can only press the button once the previous user has exited the lift.

> Elevator Entrance
Example Case:
- A user pressed the button at the level 2
- The elevator is full and directed to the level 2 to drop another user
- The user should be able to enter directly

To achieve this, the idle elevator looks like this:
```
IDLE[i:FLOORS] = (
    s[tmp:FLOORS].move_empty -> LOADING[tmp]
    // someone called the elevator and is waiting, move to the level
	|s[i].enter -> IN_CABIN[i]
    // someone is waiting at the i level, directly enter the elevator
	|alarm -> ALARM_ELEVATOR
)
```
If the elevator is at the same level both action are available, both result in the same outcome.
- If `move_empty` is performed, the elevator does a "fake move" and enters the `ENTERING` state which leads to the `SELECT` state
- If `enter` is performed, the user goes directly to the `SELECT` state.
